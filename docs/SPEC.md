## 4. 市場模型

### 4.1 核心概念：流動性（liquidity）

每檔股票有一個 `liquidity` 參數，定義為：

> **讓價格變動 1% 所需的股數。**

| 股票 | 股價 | liquidity | 買 10 股的影響 | 10 萬元能買 | 實際影響 |
|---|---|---|---|---|---|
| 台積電（大型股） | 980 | 200,000 股 | 0.005% | 102 股 | 0.05% |
| 鴻海（中型股） | 205 | 20,000 股 | 0.05% | 487 股 | 0.24% |
| 小公司（小型股） | 100 | 1,000 股 | 1% | 1,000 股 | **10%（上限）** |

**這就是你要的「有的大公司要很多人才能影響，有的一個人就能影響」。**

### 4.2 價格衝擊公式

```
impact = min( shares / liquidity × 1%, 10% )     ← 單筆最多 ±10%
新價格 = 現價 × (1 + impact)     買進
新價格 = 現價 × (1 − impact)     賣出
```

- 買進推高價格、賣出壓低價格
- 價格**永久留在新水準**（這叫價格衝擊，不是滑價）
- 單筆上限 10%，避免一筆單把價格打到 0

### 4.3 訂單型態

| 型態 | 行為 |
|---|---|
| **市價單** | 立刻以現價成交，並依公式推動價格 |
| **限價單** | 掛在 `orders` 表；市價觸及限價時才成交（成交時同樣產生衝擊） |

### 4.4 進階選項：委託簿撮合（P1，選配）

比公式更真實的做法：所有買賣單進入委託簿，價格由「最佳買價／最佳賣價」撮合產生，衝擊是撮合的結果而不是公式。

- 優點：最接近真實市場，可以講 FIFO、價格優先、部分成交
- 成本：約 2～3 倍工作量，還需要處理併發
- 決策：**先用公式版（P0）**，委託簿列為 P1；若時間夠再升級

### 4.5 時間模型：有人玩才動（lazy tick）

原本想用 Cron 每 3 分鐘跑一次，但那是「沒人也燒資源」。改成：

> **偵測到有人，才推進時間。**

```
任何 API 請求進來
  → 讀 market_state.last_tick_at
  → 若 now − last_tick_at ≥ 10 秒
       → 補跑 tick（一次最多補 5 個）
       → 更新 last_tick_at
  → 回傳最新價格
```

**好處**

- 沒人玩 = 完全靜止，不寫資料庫
- 有人玩 = 每 10 秒價格就動一次（比 3 分鐘有感）
- 免費額度幾乎用不完

**併發保護（課程重點）**

```sql
UPDATE market_state
   SET last_tick_at = ?
 WHERE id = 1 AND last_tick_at < ?
```

只有 `changes = 1` 的那個請求負責跑這一輪，其他請求直接用現價。
這就是**樂觀鎖（optimistic locking）**，可以直接寫進報告。

**缺點**：第一個人打開時會「補帳」，所以限制一次最多補 5 個 tick，避免價格一次跳太遠。

### 4.6 價格怎麼動：三個力量

純隨機漫步跑久了會漂到 0 或爆掉，所以加「均值回歸」：

```
deviation = (price − fair_price) / fair_price
drift     = −0.05 × deviation          -- 偏離 10% 就拉回 0.5%
noise     = N(0, σ)                    -- σ = 0.3%
jump      = 0.5% 機率發生 ±(2% ~ 5%)
change    = drift + noise + jump
新價      = 現價 × (1 + change)，單次限制 ±8%，最低 0.01
```

- **均值回歸** → 骨架穩定，不會越跑越歪
- **隨機噪音** → 每次打開都有小變化
- **跳躍** → 偶爾來一根大紅棒，畫面才有戲

玩家的大單則是第四個力量，直接按 §4.2 的衝擊公式加入。

### 4.7 怎麼成交？造市者（market maker）

真實市場要一買一賣才成交，但我們玩家太少，所以採**造市者模式**：

- 系統永遠願意跟你交易：你買，系統賣你；你賣，系統買回
- 價格由 4.6 的公式決定
- 買得越多，價格被推得越高（衝擊）

這是模擬股市／交易遊戲的標準做法。報告可以這樣寫：

> 本系統以造市者提供雙邊流動性，價格由衝擊模型決定；真實市場的委託簿撮合列為延伸課題。

若要「真的需要對手方」，就得做委託簿 + 造市機器人（P1）。

**快轉**：`POST /api/market/fast-forward?ticks=100`（僅開發／demo 用），
在 JS 裡算完再一次寫入，避開 Workers 的 CPU 限制。

## 5. 資料來源

| 方案 | 來源 | 費用 | 備註 |
|---|---|---|---|
| 台股歷史 | **TWSE OpenAPI**（證交所） | 免費、免金鑰 | 官方，逐檔抓每日收盤 |
| 台股即時 | TWSE 即時報價 | 免費 | 延遲 20 秒，不適合高頻 |
| 美股歷史 | Stooq CSV | 免費、免金鑰 | 直接下載 CSV |

**建議做法：歷史資料用來「校準參數」，不是用來畫圖。**

1. 用 TWSE 抓最近 30 天日線 + 最新收盤價
2. 從日線算出三個起始參數：

| 參數 | 怎麼算 | 用途 |
|---|---|---|
| `fair_price` | 30 日均價 | 均值回歸的基準 |
| `volatility` | 日報酬率標準差 | 決定噪音大小 |
| `liquidity` | 日均成交量 × 0.5% | 1% 價格衝擊的股數 |

3. 寫入 `stocks`
4. 日線本身**不畫進圖表**（tick 是 10 秒，尺度不同），圖表用快轉產生

**為什麼不直接把日線畫在圖上？**
因為時間尺度不同：日線是「每天一點」，我們是「10 秒一點」。
硬放在一起會變成「前面很平、後面很抖」的怪圖。

**但歷史資料的價值還在**：它讓每檔股票的「合理價、波動、流動性」都有真實依據，
而不是隨便寫死。這是報告可以講的一點。

**用真實資料的好處**

| 好處 | 說明 |
|---|---|
| 說服力 | 看到台積電 980、小型股 30，比看到「股票A 100」有感覺 |
| 參數有依據 | `liquidity` 從真實成交量推導，不是憑空亂設 |
| 報告加分 | 可以說「初始條件取自證交所公開資料」 |
| 股票清單現成 | 名稱、代號不用自己編 |

**成本**：寫一支匯入腳本約 2 小時，抓取可能失敗（要有 fallback）。

> 若時間不足，用一組寫死的數字也完全可以，架構不變。

## 7. 資料模型

```
accounts 1 ──< holdings >── 1 stocks
    │                           │
    ├──< orders >───────────────┤
    │                           │
    └──< trades >───────────────┘
                                │
                          price_history
```

| 表 | 主鍵 | 說明 |
|---|---|---|
| `stocks` | `symbol` | 代號、名稱、現價、**fair_price**、**liquidity**、**volatility** |
| `accounts` | `id` | 名稱、初始本金、現金、**frozen_cash** |
| `holdings` | `(account_id, symbol)` | 股數、**frozen_shares** |
| `orders` | `id` | 限價單：方向、限價、股數、已成交、狀態 |
| `trades` | `id` | 成交紀錄：方向、股數、成交價、金額、**impact** |
| `price_history` | `(symbol, ts)` | 每次價格變動（tick 或成交） |
| `market_state` | `id` | 單列：`last_tick_at`（樂觀鎖用） |

**完整性規則**

- `cash >= 0`、`shares >= 0`、`price > 0`、`liquidity > 0`（CHECK）
- `side IN ('BUY','SELL')`（CHECK）
- `orders.status IN ('OPEN','FILLED','CANCELLED')`（CHECK）
- 所有 `account_id`、`symbol` 都有 FK

**刻意的反正規化**

- `trades.price` 保存成交當時的價格，不靠 `stocks.price` 回推
- `trades.impact` 保存該筆交易造成的衝擊，報告可以直接畫圖

## 8. API 合約

| 方法 | 路徑 | 說明 |
|---|---|---|
| GET | `/api/stocks` | 行情（含漲跌） |
| GET | `/api/account?id=1` | 帳戶、持股、資產 |
| GET | `/api/trades?id=1&symbol=&side=&from=&to=&limit=20&offset=0` | 成交紀錄（可篩選、分頁） |
| GET | `/api/orders?id=1` | 我的委託 |
| GET | `/api/history?symbol=2330&hours=6` | 歷史價格（每 3 分鐘一點） |
| POST | `/api/trade` | 市價買賣 |
| POST | `/api/order` | 下限價單 |
| DELETE | `/api/order/:id` | 取消委託 |
| POST | `/api/market/tick` | 手動觸發一次價格更新（開發用） |
| POST | `/api/market/fast-forward?ticks=100` | 快轉產生歷史（僅開發／demo） |

`POST /api/trade`

```json
{ "account_id": 1, "symbol": "2330", "side": "BUY", "shares": 10 }
```

回應會附上價格衝擊：

```json
{ "ok": true, "price": 980, "newPrice": 980.5, "impactPct": 0.05, "amount": 9800 }
```

| 錯誤碼 | HTTP | 意義 |
|---|---|---|
| `INVALID_INPUT` | 400 | 參數錯誤 |
| `INSUFFICIENT_CASH` | 400 | 現金不足 |
| `INSUFFICIENT_SHARES` | 400 | 持股不足 |
| `PRICE_OUT_OF_RANGE` | 400 | 限價與現價差距過大 |
| `NOT_FOUND` | 404 | 帳戶／股票／委託不存在 |

統一格式：`{ ok: true, ... }` 或 `{ ok: false, code, message }`。

## 9. 模組設計（deep modules）

### 9.1 現況問題

`src/index.js` 394 行，混合路由、驗證、業務規則、SQL、前端。改一處要碰整支檔案，也無法單獨測試「下單」。

### 9.2 目標結構

```
src/
├─ index.js            HTTP adapter：路由與狀態碼
├─ domain/
│  ├─ trading.js       placeOrder()     ← 下單（含市價／限價）
│  ├─ market.js        applyImpact()    ← 價格形成
│  ├─ portfolio.js     snapshot()       ← 資產結算
│  └─ orderbook.js     match()          ← 限價單撮合（P1）
├─ db/
│  ├─ queries.js       所有 SQL
│  └─ schema.sql
└─ page.js             前端
```

### 9.3 介面

```js
// trading.js
placeOrder(db, { accountId, symbol, side, shares, type, limitPrice })
  → { ok: true, trade: { price, newPrice, impactPct, amount } }
  | { ok: false, code, message }

// market.js
applyImpact(db, symbol, side, shares)
  → { price, newPrice, impactPct }

// portfolio.js
snapshot(db, accountId)
  → { cash, marketValue, totalAssets, profit, profitPct, holdings }
```

**為什麼這樣切**：

- `trading` 管「一筆交易該不該成立、要動哪些表」
- `market` 管「價格怎麼變」——這是唯一需要改公式的地方
- `portfolio` 管「怎麼算資產」——唯一需要改計算公式的地方

三者可以分別替換、分別測試。刪掉任何一個，複雜度都會散回 HTTP 層。

### 9.4 接縫與測試

- `db` 由外部注入，不從 `env` 直接抓
- HTTP 層只做 request → 參數、結果 → 狀態碼
- 測試表面就是 `placeOrder` 的介面
- 工具：`vitest` + `@cloudflare/vitest-pool-workers`

## 10. 非功能需求

| 項目 | 要求 |
|---|---|
| 金額精度 | 顯示 2 位小數；內部 `ROUND(x,2)` |
| 價格精度 | 2 位小數，最低 0.01 |
| 併發 | 同帳戶同時下單不得負現金、超賣；多請求同時觸發 tick 只能有一個執行（樂觀鎖） |
| 效能 | 單一 API < 300ms（本機） |
| 額度 | Workers 10 萬 req/日、D1 5GB |

**D1 限制**：沒有跨語句互動式交易，只有 `batch()`。檢查與寫入之間有極小競態窗口，報告需說明。
