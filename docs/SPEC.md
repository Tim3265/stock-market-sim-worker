## 4. 市場模型

### 4.1 核心概念：流動性（liquidity）

每檔股票有一個 `liquidity` 參數，定義為：

> **讓價格變動 1% 所需的股數。**

| 股票 | 股價 | liquidity | 買 10 股的影響 | 10 萬元能買 | 實際影響 |
|---|---|---|---|---|---|
| 台積電（大型股） | 980 | 200,000 股 | 0.005% | 102 股 | 0.05% |
| 鴻海（中型股） | 205 | 20,000 股 | 0.05% | 487 股 | 0.24% |
| 小公司（小型股） | 100 | 1,000 股 | 1% | 1,000 股 | **10%（上限）** |

**這就是你要的「有的大公司要很多人才能影響，有的一個人就能影響」。**

### 4.2 價格衝擊公式

```
impact = min( shares / liquidity × 1%, 10% )     ← 單筆最多 ±10%
新價格 = 現價 × (1 + impact)     買進
新價格 = 現價 × (1 − impact)     賣出
```

- 買進推高價格、賣出壓低價格
- 價格**永久留在新水準**（這叫價格衝擊，不是滑價）
- 單筆上限 10%，避免一筆單把價格打到 0

### 4.3 訂單型態

| 型態 | 行為 |
|---|---|
| **市價單** | 立刻以現價成交，並依公式推動價格 |
| **限價單** | 掛在 `orders` 表；市價觸及限價時才成交（成交時同樣產生衝擊） |

### 4.4 進階選項：委託簿撮合（P1，選配）

比公式更真實的做法：所有買賣單進入委託簿，價格由「最佳買價／最佳賣價」撮合產生，衝擊是撮合的結果而不是公式。

- 優點：最接近真實市場，可以講 FIFO、價格優先、部分成交
- 成本：約 2～3 倍工作量，還需要處理併發
- 決策：**先用公式版（P0）**，委託簿列為 P1；若時間夠再升級

## 5. 資料來源

| 方案 | 來源 | 費用 | 備註 |
|---|---|---|---|
| 台股歷史 | **TWSE OpenAPI**（證交所） | 免費、免金鑰 | 官方，逐檔抓每日收盤 |
| 台股即時 | TWSE 即時報價 | 免費 | 延遲 20 秒，不適合高頻 |
| 美股歷史 | Stooq CSV | 免費、免金鑰 | 直接下載 CSV |

**建議做法：真實資料只當「起點」。**

1. 用 TWSE 抓 30 天歷史 + 最新收盤價，存進 `price_history` 與 `stocks`
2. 之後的價格由玩家交易與每日 tick 產生
3. 圖表上：真實歷史（灰色）＋ 模擬未來（藍色）

這樣既解決「圖表沒資料」的問題，又不會和「玩家會影響價格」衝突。

> 若教師要求完全自製資料，改用隨機漫步產生 30 天歷史即可，其餘不變。

## 7. 資料模型

```
accounts 1 ──< holdings >── 1 stocks
    │                           │
    ├──< orders >───────────────┤
    │                           │
    └──< trades >───────────────┘
                                │
                          price_history
```

| 表 | 主鍵 | 說明 |
|---|---|---|
| `stocks` | `symbol` | 代號、名稱、現價、**liquidity** |
| `accounts` | `id` | 名稱、初始本金、現金、**frozen_cash** |
| `holdings` | `(account_id, symbol)` | 股數、**frozen_shares** |
| `orders` | `id` | 限價單：方向、限價、股數、已成交、狀態 |
| `trades` | `id` | 成交紀錄：方向、股數、成交價、金額、**impact** |
| `price_history` | `(symbol, date)` | 每日價格 |

**完整性規則**

- `cash >= 0`、`shares >= 0`、`price > 0`、`liquidity > 0`（CHECK）
- `side IN ('BUY','SELL')`（CHECK）
- `orders.status IN ('OPEN','FILLED','CANCELLED')`（CHECK）
- 所有 `account_id`、`symbol` 都有 FK

**刻意的反正規化**

- `trades.price` 保存成交當時的價格，不靠 `stocks.price` 回推
- `trades.impact` 保存該筆交易造成的衝擊，報告可以直接畫圖

## 8. API 合約

| 方法 | 路徑 | 說明 |
|---|---|---|
| GET | `/api/stocks` | 行情（含漲跌） |
| GET | `/api/account?id=1` | 帳戶、持股、資產 |
| GET | `/api/trades?id=1` | 成交紀錄 |
| GET | `/api/orders?id=1` | 我的委託 |
| GET | `/api/history?symbol=2330&days=30` | 歷史價格 |
| POST | `/api/trade` | 市價買賣 |
| POST | `/api/order` | 下限價單 |
| DELETE | `/api/order/:id` | 取消委託 |

`POST /api/trade`

```json
{ "account_id": 1, "symbol": "2330", "side": "BUY", "shares": 10 }
```

回應會附上價格衝擊：

```json
{ "ok": true, "price": 980, "newPrice": 980.5, "impactPct": 0.05, "amount": 9800 }
```

| 錯誤碼 | HTTP | 意義 |
|---|---|---|
| `INVALID_INPUT` | 400 | 參數錯誤 |
| `INSUFFICIENT_CASH` | 400 | 現金不足 |
| `INSUFFICIENT_SHARES` | 400 | 持股不足 |
| `PRICE_OUT_OF_RANGE` | 400 | 限價與現價差距過大 |
| `NOT_FOUND` | 404 | 帳戶／股票／委託不存在 |

統一格式：`{ ok: true, ... }` 或 `{ ok: false, code, message }`。

## 9. 模組設計（deep modules）

### 9.1 現況問題

`src/index.js` 394 行，混合路由、驗證、業務規則、SQL、前端。改一處要碰整支檔案，也無法單獨測試「下單」。

### 9.2 目標結構

```
src/
├─ index.js            HTTP adapter：路由與狀態碼
├─ domain/
│  ├─ trading.js       placeOrder()     ← 下單（含市價／限價）
│  ├─ market.js        applyImpact()    ← 價格形成
│  ├─ portfolio.js     snapshot()       ← 資產結算
│  └─ orderbook.js     match()          ← 限價單撮合（P1）
├─ db/
│  ├─ queries.js       所有 SQL
│  └─ schema.sql
└─ page.js             前端
```

### 9.3 介面

```js
// trading.js
placeOrder(db, { accountId, symbol, side, shares, type, limitPrice })
  → { ok: true, trade: { price, newPrice, impactPct, amount } }
  | { ok: false, code, message }

// market.js
applyImpact(db, symbol, side, shares)
  → { price, newPrice, impactPct }

// portfolio.js
snapshot(db, accountId)
  → { cash, marketValue, totalAssets, profit, profitPct, holdings }
```

**為什麼這樣切**：

- `trading` 管「一筆交易該不該成立、要動哪些表」
- `market` 管「價格怎麼變」——這是唯一需要改公式的地方
- `portfolio` 管「怎麼算資產」——唯一需要改計算公式的地方

三者可以分別替換、分別測試。刪掉任何一個，複雜度都會散回 HTTP 層。

### 9.4 接縫與測試

- `db` 由外部注入，不從 `env` 直接抓
- HTTP 層只做 request → 參數、結果 → 狀態碼
- 測試表面就是 `placeOrder` 的介面
- 工具：`vitest` + `@cloudflare/vitest-pool-workers`

## 10. 非功能需求

| 項目 | 要求 |
|---|---|
| 金額精度 | 顯示 2 位小數；內部 `ROUND(x,2)` |
| 價格精度 | 2 位小數，最低 0.01 |
| 併發 | 同帳戶同時下單不得負現金、超賣 |
| 效能 | 單一 API < 300ms（本機） |
| 額度 | Workers 10 萬 req/日、D1 5GB |

**D1 限制**：沒有跨語句互動式交易，只有 `batch()`。檢查與寫入之間有極小競態窗口，報告需說明。
